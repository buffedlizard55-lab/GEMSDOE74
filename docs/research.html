Research notes and evaluation framework

NOT A MODEL RESULT

Historical pages made unsupported claims about why a particular score was achieved, about exact effects of fault thinning, and about validation. Those statements have been removed here. The project still needs an official-data implementation and a real holdout.

Competition objective

The official DrivenData problem description is the authoritative source for the task definition and distance-weighted Tversky metric. Before implementing or evaluating a model, inspect the current metric formulation and submission requirements directly at page 967. The project brief specifies α=0.2, β=0.8 and a 300 m triangular kernel; the exact implementation must be cross-checked against the official page and organizer reference solution.

The repo contains more than one metric module. Unit tests currently pass, but code-level tests alone do not prove equivalence to the organizer's scorer. Validate hand calculations and compare with the reference solution before trusting any holdout number.

Why sparse output is a hypothesis, not an explanation

A distance-weighted scoring rule can make redundant output pixels costly relative to their incremental credit. That makes spatially selective thinning a plausible experimental strategy. It does not establish that the named GEMSDOE32 file earned 0.2778, nor that a particular disk spacing or catalogue buffer caused it. The attribution and mechanism need a receipt, original raster, exact evaluator and controlled ablation.

See the 0.2778 attribution review for the distinction between metric intuition and evidence.

Required hide-and-recover design

  1. Withhold whole fault segments and a buffer, not random catalogue pixels.
  2. For each fold, derive every catalogue-dependent feature only from the visible fault segments.
  3. Mask visible faults pixel-exactly from the scored area.
  4. Use pooled DTI with the official α, β, and kernel; report evaluator version, withheld-positive count and confidence interval.
  5. Run a feature-alone leakage canary, with AUC >0.90 treated as leakage until explained.
  6. Compare controls and incumbent on the same folds; only then evaluate final registry correlation/overlap.

The present scripts do not meet this protocol and now fail closed.

Data and provenance

The actual official feature stack, labels, and sample submission are absent from `data/`; the competition data tab is login-gated. No proxy copy is accepted as a substitute without recorded rights and provenance. The official sources and known access limitations are listed on the sources page.

Research status is negative until official data and compliant evaluation are available.
