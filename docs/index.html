Why “zeros” vs “nan”?

The competition accepts both. The organizer's training_features.tif uses -3.402823e+38 as nodata; copying that sentinel through triggers the same error. A file with nodata=NaN and NaN cells outside the footprint is legal but one validator change away from rejection. What happens after you submit?

DrivenData scores your file on a hidden fault set (never released) using the Distance-Weighted Tversky Index (DTI): DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w) with 300 m triangular kernel. Known USGS/INGENIOUS faults are masked (not scored) — only new faults count (organizer clarification Thread 11516). Your score appears on the leaderboard. You have 3 scored submissions per week; the Round 1 file is also scored in Round 2.

Why did h33-h33-2-b2 score 0.2778 and can we beat it? (PhD-level assessment)

Why 0.2778 is the family high

The metric is a budget: DTI = T / (0.2·(T+F) + 0.8·|G|) so the denominator grows by exactly 0.2 per emitted dot (dD = 0.2·(dT+dF) = 0.2), while the numerator grows by the dot's kernel credit k ∈ [0,1]. A dot improves DTI iff k > 0.2·DTI (derived in src/gems74/metric.py:marginal_inclusion_threshold; GEMSDOE32 IR-32-BAR-01). At 0.27 the bar is 0.054. The only lattice kernel weights near that are the (2,2)-diagonal 1−2√2/3 = 0.05719.

H33-2-B2 is not a new detector — it is a packing optimizer: it starts from the group's best live-scored surface (40,199 dots, owner-reported 0.2708 via dotted-H19-5-d2.8 + Poisson300m) and deletes every dot within 2 px (200 m) of the catalogue. Those dots were “free” in the old holdout (visible faults were masked without FP penalty) but are expensive live (the hidden set is off-catalogue, so catalogue-near mass is FP). Deleting them raises credit per emitted pixel without moving the geometry — exactly the budget optimum.

Empirically: GEMSDOE25 H19-5 (121,131 px → 0.1922) → d1.5 (60,069 px → 0.2477) → d2.8 (44,090 px → 0.2600) → H33-2-B2 (37,654 px → 0.2778) — same field, thinning monotonically increases DTI while k > 0.2·s.

Can we beat 0.2778? (and 0.4413?)

Short answer: only by raising credit density — i.e., a better spatial ranking, not more mass. At fixed 39.5k dots, 0.2778 → 0.4413 requires +59% mean k (0.4413/0.2778 − 1). No re-packing of the same ridge field can supply that; the field's enrichment of the SGMC off-catalogue population is only 1.4× over background [MEASURED, GEMSDOE32].

This submission tries a different field: blind faults that have no scarp but have hydrothermal plumbing (springs + K-metasomatism). Its distinctiveness is measured: Spearman ρ = −0.0009, 6.2% dot overlap within 300 m vs H33-2-B2 — far below the 0.90 / 70% duplicate thresholds. Holdout validation on the catalogue-masked instrument is negative (HOLDOUT-DTI 0.0016 vs 0.031 random) — expected: the catalogue-masked holdout cannot reward genuinely new faults (IR-32-PROXY-01) and its ρ vs live is only +0.087 [MEASURED, GEMSDOE32 evidence/instrument_calibration.json]. The drift-corrected instrument (ρ=+0.51 vs live) is the better predictor, but with n=12 it is not significant (p≈0.09).

Projection (not a score): live-mirror + SGMC calibration suggests a ceiling of ~0.30–0.33 at equal mass if the spring/alteration signal carries 2× enrichment — but this is a model, never written as a score. Only the organizer board is truth.

How the portal error is fixed

DrivenData rejects files whose nodata tag is -3.402823e+38 or whose outside-footprint cells are NaN if the validator is strict — both count as “outside [0,1]”.

  • Mechanism 1 — float32 sentinel: training_features.tif uses -3.4e38 for 3,061 valid footprint cells; copying it through leaks it into the submission.
  • Mechanism 2 — NaN sentinel: sample_submission.tif uses NaN outside the footprint (7,111,787 cells); a submission with NaN is legal but one validator change away from rejection.

Fix here: this file is written all-finite with nodata=None — outside-footprint cells are 0, not NaN or sentinel — verified by re-opening the bytes (receipt above). It cannot trigger “Predicted values must be in range [0, 1]”.
