How to submit a GEMS prediction GeoTIFF

Current state: BLOCKED — there is no GEMSDOE74 TIF to download. Do not submit a file from this repository. The competition inputs, shared evaluator/writer, validated candidate, and submission receipt are absent.

This page is the safe upload checklist for when a validated artifact exists. The landing page must show a live, auditable READY TO SUBMIT state before a download appears. This build intentionally has no download link.

Before downloading anything

  1. Open the GEMSDOE74 overview. Proceed only if the status is explicitly READY TO SUBMIT and a file, SHA-256 digest, validation receipt, and unique name are shown together.
  2. Confirm the candidate beat the current spatial-holdout best under the preregistered evaluation. Confirm that feature leakage checks, registry-correlation and dot-overlap checks, and TIFF validation all passed.
  3. If the page says BLOCKED, NOT RUN, PROJECTED, or UNSCORED, stop. Do not use an older GEMSDOE site's file as a substitute.

Upload steps in DrivenData

The requirements below are transcribed from the competition form text included in the project brief. Recheck the official competition rules and the live form before uploading; those pages could not be fetched in this workspace.

  1. Sign in to the competition on DrivenData and open its New submission form.
  2. For File to submit, select the validated single-band GeoTIFF (.tif) or a ZIP containing exactly one GeoTIFF, if the current form still permits both.
  3. Use the unique name shown on the GEMSDOE74 artifact receipt. A naming template—not a real submission name—is GEMSDOE74-<method>-<sha256-first-8-lowercase>.
  4. Paste the short, evidence-labelled note shown on the receipt. Project convention: keep it at or below 140 characters and say whether the artifact is unscored; do not call a projection a score.
  5. Submit only if the file has already passed the project's independent validation. After submission, save the organizer's submission-page receipt and record its exact score and submission identifier separately from holdout results.

The competition form description supplied in the brief says the raster must match the submission format's CRS, shape, and geotransform. Those values must be read from the official sample submission; they are not available in this checkout. Do not infer geometry from another project's file.

Preventing “Predicted values must be in range [0, 1]”

The error text is reported by the user in the initiating brief. The project must catch it before upload, not by asking the user to repair a raster manually.

  • Use the shared submission writer and validator; do not edit a TIFF in a GIS application as a workaround.
  • Re-read the written file from disk. Check that all prediction values inside the valid footprint are finite and within the allowed closed interval, and that the raster has the expected single band.
  • Check that the CRS, dimensions, pixel size, transform, and footprint match the official sample-submission raster exactly.
  • Keep nodata/NaN handling consistent with the official format. A visually plausible map is not evidence of a valid upload.
  • Archive the validator output, candidate SHA-256, writer version, input hashes, and the exact submission note with the artifact.
Important: clipping values into range without examining the model output can hide a scaling, nodata, or mask bug. Fail validation and fix the upstream cause; do not silently clip and declare success.
