How to submit a GEMS prediction GeoTIFF

Current state: BLOCKED — no artifact is cleared for submission. An earlier H74-A experimental TIF is archived in this repository, but its recorded holdout is negative and lacks the required buffer and confidence interval. Its format receipt does not authorize a competition submission. This branch created no new TIF.

This page is the safe upload checklist for when an artifact exists and has passed every gate. The landing page must show a verifiable READY TO SUBMIT state before a download appears.

Before downloading anything

  1. Open the GEMSDOE74 overview. Proceed only if it explicitly says READY TO SUBMIT and displays the file, SHA-256, validator receipt, holdout evidence, unique name, and note.
  2. Confirm the candidate beat the current spatial-holdout best under the preregistered evaluation. Confirm feature-alone leakage checks and both pre-placement and final-dot registry comparisons passed.
  3. If the page says BLOCKED, NOT RUN, PROJECTED, or UNSCORED, stop. Do not use a previous GEMSDOE file as a substitute.

Upload steps in DrivenData

The requirements below are transcribed from the competition form text included in the project brief. Recheck the official competition rules and live form before uploading; those pages could not be fetched in this workspace.

  1. Sign in to the competition on DrivenData and open its New submission form.
  2. For File to submit, select the validated single-band GeoTIFF (.tif) or a ZIP containing exactly one GeoTIFF, if the current form permits both.
  3. Use the unique name printed on the artifact receipt. Naming convention—not a real submission name—GEMSDOE74-<method>-<sha256-first-8-lowercase>.
  4. Paste the short, evidence-labelled note from the receipt. Project convention: keep it at or below 140 characters and mark an unscored artifact as such; never call a projection a score.
  5. Submit only after all local gates pass. Save the organizer submission-page receipt and record its exact score and submission identifier separately from holdout results.

The competition form description supplied in the brief says the raster must match the official submission grid's CRS, shape, and geotransform. Read them from the competition's sample raster; do not infer them from a sibling project.

Preventing “Predicted values must be in range [0, 1]”

The error text is reported by the user in the initiating brief. Catch it before upload, not by asking the user to repair the raster manually.

  • Use the shared writer and independent validator; do not hand-edit a TIFF in a GIS application as a workaround.
  • Re-read the written file from disk. Verify that values inside the valid footprint are finite and within the allowed closed interval, and verify the raster band count and type.
  • Compare CRS, dimensions, pixel size, transform, and footprint exactly with the official sample-submission raster.
  • Keep nodata/NaN handling consistent with the official format. A visually plausible map is not evidence of a valid upload.
  • Archive validator output, candidate SHA-256, writer version, input hashes, and the exact submission note beside the artifact.
Do not silently clip. Clipping values into range can hide scaling, nodata, or mask bugs. Fail validation, diagnose the upstream cause, and regenerate through the shared writer.
