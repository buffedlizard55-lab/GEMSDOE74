2. Why a sparse file can score high

Let T = distance-weighted true-positive credit, F = distance-weighted false-positive mass, G = number of truth pixels, and N = weighted false negatives. The published definition gives N = G − T (each truth pixel either earns its best kernel credit or counts as a miss). Substituting into the metric:

DTI = T / (T + 0.2·F + 0.8·N)
    = T / (0.2·T + 0.2·F + 0.8·G)        since N = G − T

Three things follow, and each is algebra, not a claim about geology.

  1. G is fixed. The score rises only with T (credit captured) and falls with F (mass that earns nothing). Extra dots never reduce N beyond their credit.
  2. A dot pays only through the kernel. A dot at distance d from the nearest hidden fault earns credit c = max(1 − d/300 m, 0) and costs 1 − c in F. Its credit is at most 1 and falls to 0 at 300 m.
  3. Sparse, well-sited files can beat dense ones. A dense file that covers a corridor earns credit on each dot but also pays 1 − c on each. A pruned file keeps only dots with high expected credit. This is why thinning can raise the score, and why a file with 37,654 dots can be competitive. GEMSDOE32's own pruning evidence (its d28 autopsy) points the same way, but that evidence is on its proxies, not on the organiser.

INFERENCE Removing dots that sit within 200 m of the known catalogue can help if the hidden faults are mostly away from the catalogue. It can also hurt, because faults cluster and a dot 200 m from a catalogue fault may still earn credit. This is an empirical question. The public record cannot settle it.

3. The break-even rule (derived here, tested in the repo)

Add one pixel with probability 1 that earns credit c against an otherwise uncovered truth pixel, and whose distance to every other truth pixel is at least 300 m. Then:

  • TP rises by c. FN falls by c. FP rises by 1 − c.
  • The denominator TP + 0.2·FP + 0.8·FN therefore changes by c + 0.2(1 − c) − 0.8c = 0.2. The c terms cancel exactly.
  • So DTI rises if and only if (T + c) / (D + 0.2) > T / D, i.e. c > 0.2 · DTI.

4. Can we beat 0.2778?

On the public board: 0.2778 is rank 47. Ranks 1–46 are all above it, and the top-5 public cut is 0.3539. Beating 0.2778 is therefore a rank-47 target, not a prize-level target. Prizes are decided on the private test set and on the expanded label set, which the public board does not show (rules §3.6).

On our side: we cannot score a candidate yet, so no claim of beating 0.2778 is made. To make one, we need (1) the official feature stack, (2) our evaluator run on a spatially blocked holdout with a withheld-positive count and a 95% confidence interval, and (3) a candidate whose emitted dots have mean credit above 0.2 times the incumbent's holdout score. Until (2) exists, the incumbent is undefined, so there is nothing to beat in our own terms.

Verdict: NOT SHOWN Plausible as a target, unproven as a result.

5. What this changes in our plan

  • Score the emitted set by its expected credit per dot, not by how many dots it contains. Keep a dot only when its expected credit clears 0.2·s.
  • Test every idea on a holdout that is spatially blocked and withholds whole fault segments with a buffer, so that catalogue-derived features cannot see the held-out faults. The metric itself is implemented here and unit-tested.
  • Do not spend a weekly slot on a file that has not beaten the incumbent on the holdout.

6. What we did not establish

  • That 0.2778 belongs to any GEMSDOE file.
  • That any GEMSDOE file was accepted by the organiser. The format is correct, but the platform's acceptance was not observed.
  • Anything about the private test set, which decides Phase 1.
  • Whether the mechanisms above hold on the real hidden faults. They are derived from the metric's definition, and the score tests show only that the algebra is right.
